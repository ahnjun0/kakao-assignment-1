# VanillaJS Todo App

## 프로젝트 소개

VanillaJS만 사용하여 구현한 Todo 앱입니다. 카카오테크캠퍼스 1차 과제 제출물입니다.

## 사용 기술

- HTML
- CSS (커스텀 프로퍼티)
- Vanilla JavaScript
- Web Storage API (localStorage)

## 폴더 구조

```
todo-vanilla/
├── index.html   # 마크업 구조
├── style.css    # 스타일 (메인 컬러 #672be0)
├── app.js       # 상태 관리, 렌더, 이벤트
└── README.md
```

## 주요 기능

- [X] Todo 생성 / 조회 / 수정 / 완료 / 삭제 (CRUD)
- [X] 상태별 필터링 (전체 / 진행 중 / 완료)
- [X] 날짜별 Todo 관리 (일간 뷰)
- [X] localStorage 영속화
- [X] (도전) 주간 뷰 — 월~일 그리드 + 날짜별 `완료/전체` 카운트
- [X] 달력 팝오버로 자유 날짜 이동
- [X] "오늘로 가기" 빠른 이동 버튼
- [X] 체크박스 UI + 완료 항목 하단 정렬
- [X] 다크 모드 (시스템 설정 자동 감지 + 수동 토글)
- [X] 인라인 수정 (더블클릭 또는 수정 버튼 → Enter · 확인 버튼 저장 / Esc 취소 / blur 자동 저장)

## 실행 방법

VSCode Live Server 등 정적 서버로 `todo-vanilla/index.html` 을 연다.
`file://` 로 직접 여는 방식은 일부 환경에서 동작이 다를 수 있다.

## 설계 메모

- 상태(`todos`, `selectedDate`, `currentFilter`)는 `app.js` 상단에서 한 곳으로 관리한다.
- 상태 변경 후 `render()` 한 번으로 화면을 다시 그린다. (React 전환을 염두에 둔 단방향 흐름)
- 순수 함수(`formatDate`, `getVisibleTodos`)와 DOM 조작을 분리한다.
- 리스트 클릭은 이벤트 위임(`$list.addEventListener`)으로 처리한다.

## 구현하면서 어려웠던 점

- **날짜 처리의 함정**: 처음엔 무심코 `toISOString().split("T")[0]`을 쓰려고 했는데, 이게 UTC 기준이라 한국시간 자정 근처에서 하루가 밀린다는 사실을 알게 됐다. 결국 `formatDate(date)`로 로컬 시간 기준 포매터를 직접 만들었고, 비교/저장은 전부 `YYYY-MM-DD` 문자열로 통일했다.
- **주간 뷰의 월요일 시작**: JS의 `Date.getDay()`는 일요일이 0인데, 우리 주간 뷰는 월요일 시작이라 일요일에만 `-6`을 따로 빼주는 분기가 필요했다. 처음엔 모든 요일에 `1 - day`를 했다가 일요일이 다음 주 월요일로 가버려서 헤맸다.
- **`setMonth()` 롤오버**: 달력 만들 때 1월 31일에서 +1개월 하면 2월 31일이 없으니 3월 3일로 가버리는 문제가 있었다. `setDate(1)`을 먼저 호출해 1일 기준으로 이동하도록 해서 해결했다.
- **다크 모드 FOUC**: `app.js`가 body 끝에서 실행되니까 새로고침할 때 라이트 → 다크로 깜빡이는 현상이 있었다. `<head>` 안에 작은 인라인 스크립트로 `data-theme`을 미리 세팅해 해결했다.
- **상태 동기화 설계 판단**: 주간 뷰와 일간 뷰가 서로 영향을 줘야 하는데, 처음엔 `weekStartDate`를 따로 둘까 했다가 `selectedDate` 하나만 진실의 출처로 유지하고 주(週)는 매번 계산하도록 했다. 동기화 버그가 원천적으로 사라졌다.

## AI 활용 내용

- 초기 단계에서 "VanillaJS Todo의 큰 청사진과 기초 파일 구조를 잡아달라"고 요청해 `index.html` / `style.css` / `app.js` 골격과 디자인 토큰을 빠르게 세팅했다.
- 기능을 한 단계씩 추가할 때마다(CRUD → 필터 → 일간 뷰 → localStorage → 주간 뷰 → 달력 → 다크 모드) AI에게 코드를 제안받고, 항상 **"왜 그렇게 짰는지"**를 짧게 설명받아 내가 코드를 읽고 이해할 수 있는 형태로 받았다.
- 설계 분기점(예: "달력을 어떻게 넣을까", "주간 뷰 카운트를 어떻게 표시할까")에서는 AI에게 옵션을 비교해달라고 해서 트레이드오프를 확인한 뒤 내가 골랐다.
- 에러나 의도와 다른 동작이 있을 때 AI에 코드와 증상을 같이 전달해 원인을 같이 찾았다.

## 직접 수정한 부분

- 주간 뷰의 카운트를 단순 `n개`에서 **`완료/전체` 비율 표기**(예: `2/5`)로 바꾸도록 직접 변경했다. 진행도가 한눈에 보이게 하고 싶었고, 모두 완료된 날은 흐리게 처리해서 "끝난 날"을 구분되게 했다.
- 빈 상태 메시지가 필터에 따라 다른 문구가 나오도록 직접 수정했다 ("진행 중인 할 일이 없습니다." vs "완료된 할 일이 없습니다." vs "이 날짜에 등록된 할 일이 없습니다.").
- AI가 처음 제안한 인라인 위치/순서를 그대로 두지 않고, **달력 팝오버를 날짜 라벨 클릭 시 열리는 형태**로 UX를 직접 골랐다 (상시 표시 / 토글 옵션 비교 후).
- 다크 모드에서 `--color-primary`(#672be0)는 그대로 두는 쪽을 직접 택했다. 브랜드 컬러는 두 모드 공통이어야 자연스럽다고 판단했고, `--color-primary-soft`만 진보라(`#2a1f4a`)로 교체했다.
- 처음엔 `prompt()`로 수정 다이얼로그를 띄웠지만 UX가 너무 어색해서 **인라인 편집**으로 다시 만들었다. 더블클릭이나 `수정` 버튼으로 그 자리에서 input으로 전환되고, Enter로 저장 / Esc로 취소 / 포커스 잃으면 자동 저장되도록 했다. 이벤트 위임만 쓰던 다른 부분과 달리 keydown은 input에 직접 리스너를 다는 게 더 자연스러워서 일관성보다 적절함을 택했다.

## 배운 점

- **상태 단일 출처와 단방향 흐름**: `todos`, `selectedDate`, `currentFilter` 같은 상태를 한곳에서 관리하고 `render()` 한 번으로 화면 전체를 다시 그리는 패턴이, 코드량은 살짝 늘지만 버그가 들어올 자리가 확연히 줄어든다. React 사고방식을 Vanilla로 미리 연습한 셈이다.
- **순수 함수와 DOM 조작 분리**: 날짜 유틸(`formatDate`, `shiftDate`, `getWeekDates` 등)과 필터링(`getVisibleTodos`)을 순수 함수로 떼어내니, 머릿속에서 추적하기 쉽고 나중에 React로 옮길 때도 그대로 복사하면 된다는 감이 잡혔다.
- **CSS 변수로 만드는 디자인 시스템**: 색·간격·라운드를 `:root`에 토큰으로 잡아두니, 다크 모드를 `[data-theme="dark"]`에서 변수만 덮어쓰는 단 한 블록으로 끝낼 수 있었다. 컴포넌트 CSS는 한 줄도 고치지 않고 구현할 수 있었다.
- **이벤트 위임**: li마다 리스너를 다는 대신 부모 `ul`에 한 번만 다는 패턴이 새로 렌더된 항목에도 자동으로 적용된다는 점에서 강력했다. `data-action`/`data-id`로 의도를 markup에 담는 방식도 익숙해졌다.
- **JS의 Date 다루기**: 로컬 시간 vs UTC, `getDay()`의 일요일=0, `setMonth()` 롤오버처럼 함정이 많은 영역이라는 걸 직접 부딪치며 배웠다. 비교 가능한 문자열 포맷으로 통일하는 게 정신 건강에 좋다.
- **AI를 협업자로 쓰는 법**: 큰 구조와 트레이드오프는 같이 논의하되, 디테일과 결정은 내가 한다는 분업이 가장 결과가 좋았다. 한 번에 전체를 받기보단 기능 단위로 끊어 받고 매번 브라우저로 확인하니 코드 이해도가 유지됐다.
